# Purpose
Produce per-subdomain slices: subdomains, bounded contexts, ubiquitous language, owned invariants, source-of-truth concepts, domain events. Stop at `blackboard/domain/`; no context map, no tactical DDD, no packages/APIs/schemas/infrastructure, no invented requirements.
Subdomain = expertise area; bounded context = one boundary, one model; aggregates listed only as consistency candidates.
# Workflow
1. Extract: read twice (outcomes/actors/flows; nouns/verbs/rules/events/quantities). Per term: definition, actors, synonyms/overloads. Keep user words.
2. Capabilities: group verbs/outcomes; own rules+lifecycle+owner = boundary signal.
3. Split on signals, not entities: language, rule/lifecycle ownership, actor change, cadence, data ownership, consistency, regulatory. **Cohesion guard - signals split contexts first, subdomains only on expertise**: these signals locate a BOUNDED CONTEXT; a new SUBDOMAIN opens only when the knowledge area, the business outcome or the actors genuinely differ. Differing cadences, lifecycles, or consistency needs inside ONE cooperating workflow - steps that exist only to serve the same described outcome - are contexts (or responsibilities) of the SAME subdomain, never separate subdomains. Subdomain count follows the distinct capabilities the description names, not the number of verbs or rhythms it uses; re-deriving a subdomain from every workflow step is the one-context-per-entity error wearing a strategic hat (2026-11-26 live: a short single-outcome description became three subdomains split on cadence alone, and every later phase paid per slice).
4. Classify: core = differentiator (deepest modeling); supporting = necessary/specific; generic = buy/reuse. Name by capability, never tech.
5. Contexts: name, responsibility, in/out scope, language, invariants, source of truth, publishes/consumes, reads (optional, step 6), actors, external systems, confidence. One meaning per term per context; one owner per invariant; strong consistency inside; never a context per entity/table; never merge unrelated rules to shrink count. **One home per cross-cutting access policy**: a tenancy/ownership/authorization rule guarding a shared resource is an OWNED invariant of exactly one boundary - the one that admits the traffic to that resource. Any other context that behaves under it records the dependence as an interaction (consumes/reads) or an out_of_scope line ("access enforced by X") - never as its own reworded invariant: restating "the same rule in other words" evades the one-owner law by thesaurus and makes two boundaries co-responsible for one decision the first time an update touches one of them.
6. Interactions, two channels - never one faking the other: `publishes`/`consumes` carry DOMAIN EVENTS ONLY: significant occurrences that already happened, delivered asynchronously, producer + likely consumers, names only. A synchronous prerequisite needed inside one ongoing interaction - context A must read context B's current answer before it can do its own work - goes in A's optional `reads` list, naming B (or the external source). Do not mint an event pair or a published/completed handshake for a direct read: that invents an asynchronous lifecycle the description never stated and hands the architect a pub/sub loop to build where a call belongs (2026-11-26 live: an in-interaction assembly modeled as a TurnStarted/TurnCompleted event cycle).
7. Validate: one owner per invariant; significant terms placed or flagged; nothing invented; uncertainty as Assumption|Ambiguity|Open question with boundary impact. **Transport posture is a modeled fact**: for every inbound flow, record whether delivery is at-most-once or at-least-once (retries, redelivery, network replay) and, when the flow writes an append-only/correcting history, which identity makes a retry distinguishable from a new event (client-supplied key, natural business identity, or an explicit accept-duplicates declaration). A capability described as "ingest, corrections append revisions" over an at-least-once delivery, with no dedup identity named, is an UNRESOLVED AMBIGUITY worth a boundary question - not an assumption to silently invent (seed-002 2026-11-16: server-minted ids over an at-least-once delivery made every retry mint a domain revision the device never sent twice). **Ask the axis question, not just the identity question**: when the candidate identity is natural (device, metric, timestamp - not a client token), the Ambiguity item must spell out the decision the later dedup duty will have to make - is the MUTABLE PAYLOAD (the corrected value) part of that identity, or excluded, and what then separates a retry from a correction? An ambiguity recorded without the axis phrasing gets resolved by omission downstream: the plan satisfies the idempotency rule with a value-excluding identity and the description's corrections silently become no-op duplicates - nobody ever decided, so nobody ever said so (2026-11-16 PART III G2). **Seed fidelity**: every entity, metric, named range/threshold and status literal the description spells out must appear VERBATIM in some context's language or invariants, or the deviation must be recorded as a named Assumption with its reason - substituting vocabulary the description never used (another sensor family, renamed flags, different boundary numbers) creates a wrong world that stays internally consistent and is invisible to every downstream gate, because all later validators check coherence, not fidelity (2026-11-16: an athletic-telemetry seed produced weather-metric enums; 71 tasks and every green test inherited the drift). **Cohesion and attribution checks** (the validator greps words, not intent - these are yours): every subdomain's `why_distinct` must cite an expertise/language/actor/outcome difference, never a cadence or lifecycle variety inside another slice's workflow; each cross-cutting access policy appears as an owned invariant in exactly one slice; and a security/AI directive quote must be a sentence the description states FOR THIS slice's own capability - one capability, one owning slice, one directive (pasting the sibling's sentence here because this slice feeds it is a misplacement no engine check can see). Quantities the description NAMED but never bounded (metrics without ranges) are inventoried - each one a flagged Assumption with its honest posture (unbounded, or disabled pending an answer) and collected in a single operator-facing list, not scattered: the deviation rule above must keep them from inventing a range, and the enumeration must keep the disabled posture from being a silent, thrice-repeated surprise instead of one answered decision (PART III: unnamed valid ranges shipped `enabled:false` three times with no operator ever asked).
# Output
One `domain-boundary-<slug>.json` per subdomain, exact slice keys per the specialist contract; valid JSON; unique context names; thin input => best-effort + assumptions; `question` only for boundary-changing unknowns. Optional security_directive{required,quote,source:"description"}: record it ONLY when the description itself states the domain needs no security, copying that sentence VERBATIM into `quote` (the engine greps the description file named in metadata.source_description - a paraphrase or an invented waiver is refused). Absent = SECURITY REQUIRED, the default; never omit a directive to mean "not needed". Optional ai_directive{required:true,quote,source:"description"}: the mirrored trigger, opposite polarity - record it ONLY when the description itself states that THIS subdomain - the very slice being written - carries an AI capability (generation, summarization, embedding, retrieval-augmented answers, agentic or tool-calling flows), the sentence copied VERBATIM and describing that slice's own capability, never lifted from a sibling slice's paragraph because this slice merely feeds or assists the capable one (the engine greps the words and refuses a paraphrase; the attribution is yours to get right; `required` must be true). Absent = NO AI capability: the AI phase never runs on inference, and required:false is refused because not-wanted IS the absent default.
