# PulseStream Engine — Telemetry Ingestion & Processing

High-throughput, non-blocking ingestion and real-time processing of 1 Hz time-series
telemetry from athletic edge devices. One Spring Boot reactive service covering the
**Telemetry Ingestion & Processing** bounded context: boundary validation, backfill
reordering against device clocks, an append-only revision history, correlation and
audit on every packet, and backpressure-aware event broadcasting.

Generated by the Blackboard pipeline (seed `002_description.md`), drain of 2026-11-17:
63 planned units, every unit closed green, boot and request-path gates proven on the
delivered bytes.

## Quick start

```bash
cd services/telemetry-ingestion-processing

./mvnw test                        # the full delivered suite: 131 tests, 20 classes
./mvnw -o -DskipTests package      # build the executable jar
java -jar target/telemetry-ingestion-processing-0.0.1-SNAPSHOT.jar
# the jar boots from ANY working directory: migrations travel inside it (classpath)
```

The service starts on port 8080 (`--server.port=...` to move) and needs **no
environment variables** — see [Runtime & configuration](#runtime--configuration).

```bash
curl -i -X POST localhost:8080/api/v1/telemetry/packets \
  -H 'Content-Type: application/json' -H 'X-Request-Id: demo-1' \
  -d '{"deviceId":"dev-9","samples":[{"metric":"heart_rate","tDevice":"2026-01-01T10:00:00Z","value":72}]}'
# HTTP/1.1 202 Accepted
# X-Request-Id: demo-1
# {"accepted":1}
```

## HTTP contract

`POST /api/v1/telemetry/packets` — one JSON object per request.

```json
{ "deviceId": "dev-9",
  "samples": [ { "metric": "heart_rate", "tDevice": "2026-01-01T10:00:00Z", "value": 72 } ] }
```

| Case | Result |
|---|---|
| Valid packet | `202 Accepted`, body `{"accepted":<n>}` (n = samples buffered into the stream; persistence follows within one reorder window) |
| Blank `deviceId`, empty `samples`, malformed JSON | `400 application/problem+json` with field errors; **nothing is persisted or audited as accepted** |
| Out-of-range sample | `202` — the payload is **kept**, tagged `VALIDATION_FAILED`, never dropped |
| Duplicate retransmission (same device+metric+tDevice) | `202` — appended as a **new revision** (at-most-once posture, see below) |

`X-Request-Id`: adopted from the request header, or generated (UUID) if absent; echoed
on the response, carried through the reactive pipeline via the Reactor Context
(`requestId`), written to every audit row and every structured log line. The endpoint
handler is `@Controller`-annotated and component-scan registered
(`TelemetryIngestController`).

## Processing pipeline

```
POST ─▶ IntakeService (bounded sink, capacity 1024, never blocks)
        └ audit(actor=device, action=ingest, outcome=accepted|overflow)
        ▼
      ValidationService — physical boundaries per metric (below)
        ▼
      ReorderingService — windowed by t_device, then appended chronologically
        ▼
      EventLogService ─▶ R2dbcEventLogRepository (append-only revisions)
                     └▶ SinkEventBroadcast (downstream stream, bounded)
        ▼
      audit + structured ECS log lines at every step
```

Wiring: `PipelineConfiguration.telemetryPipeline` subscribes
`intake → validate → buffer(reorder-window-seconds) → reorderWindow → append`.

### Sensor metric boundaries (seed-literal, externalized in config)

| Metric | Rule | Config keys (`telemetry.*`) |
|---|---|---|
| `heart_rate` | 30 – 240 BPM inclusive | `heart-rate-min` / `heart-rate-max` |
| `power` | 0 – 2500 W inclusive | `power-min` / `power-max` |
| `cadence` | 0 – 220 RPM inclusive | `cadence-min` / `cadence-max` |
| `swim_pace` | **> 45** sec/100 m (lower bound exclusive) | `swim-pace-min-exclusive` |
| others (e.g. `ground_contact_time`, `respiration`) | **unbounded — accepted** (the seed names no limits; see [Decision list](#decision-list-operator)) | — |

Failing a boundary sets status `VALIDATION_FAILED` and **keeps the value**; statuses are
the shipped constants of `TelemetrySample`: `PENDING` (pre-validation, never null) →
`VALID` / `VALIDATION_FAILED`.

### Backfill reordering (the seed's core rule, live in the request path)

* Samples are buffered for `reorder-window-seconds` (60 s) and flushed as a window;
  each window is sorted **ascending by `t_device`** (never by `t_ingress`, stable
  order), so out-of-order packets are re-indexed chronologically before persisting.
* A sample whose `t_device` is earlier than a higher one already seen in its window is
  a **backfill**: counted `telemetry.reordering.late{kind=in_window}`, step log
  `reordering.backfill.applied`.
* A sample with `t_ingress − t_device > window` is still appended, counted
  `telemetry.reordering.late{kind=beyond_window}`.

### Append-only history & duplicate posture

`telemetry_record` PK is `(device_id, metric, t_device, revision)`. The first write for
a key is **revision 1** (`kind=RECORD`); every later write — correction, backfill **or
retransmission** — appends `max(revision)+1` (`kind=REVISION`) and never touches
earlier rows. The delivery posture is **at-most-once inbound with no dedup identity**:
a network retry of an identical payload is indistinguishable from a correction and
also appends a revision — consumers must be idempotent and read the highest revision
per key (`findLatest` returns exactly that).

## Observability

**Step logs** (structured key-values `step`, `correlationId` via SLF4J fluent API,
ECS JSON on the file sink): `intake.packet.received`, `validation.sample.validated`,
`validation.sample.failed`, `reordering.window.flushed`, `reordering.backfill.applied`,
`eventlog.record.appended`, `eventlog.revision.appended`, `eventlog.broadcast.published`.

**Metrics** (all bounded tags — no device ids):

| Meter | Type | Tags / meaning |
|---|---|---|
| `telemetry.intake.packets` | counter | `outcome=accepted\|overflow` |
| `telemetry.validation.samples` | counter | `status=valid\|failed` |
| `telemetry.reordering.late` | counter | `kind=in_window\|beyond_window` |
| `telemetry.eventlog.appended` | counter | `kind=record\|revision` |
| `telemetry.pipeline.dropped` | counter | `stage=intake\|eventlog\|broadcast\|audit` — every drop/refusal is counted |
| `telemetry.pipeline.latency` | timer | `stage=reordering` |

**Audit trail**: one row per accepted/overflow ingest (`device`/`ingest`), per append
(`eventlog`/`append`/`success|failure`) — failures are audited **and** counted.

**Export for external tools**: ECS JSON lines to the local rolling file
`logs/telemetry-ingestion-processing.log` (10 MB, 14 files, configured via
`logging.structured.format.file=ecs`, `logging.file.*`); the platform shipper (Filebeat
/ Elastic Agent class) moves them — there is **no** hard runtime dependency on any
external cluster and the app boots and passes its suite with no shipper present.

**Correlation**: Reactor Context (`contextWrite("requestId")` at the WebFilter) plus the
explicit `correlation_id` column and log field. No MDC / context-propagation library is
installed — the strategy declares that posture explicitly; correlation on log lines
travels via the explicit field, not thread-locals.

## Runtime & configuration

Every operational value is externalized (`telemetry.*` in
`src/main/resources/application.yml`, bound by the `TelemetryProperties` record):

```yaml
telemetry:
  reorder-window-seconds: 60     buffer-capacity: 1024
  heart-rate-min: 30             heart-rate-max: 240
  power-min: 0                   power-max: 2500
  cadence-min: 0                 cadence-max: 220
  swim-pace-min-exclusive: 45
```

**Configuration posture (disclosed):** the base document spells the embedded H2
datasource as its default (`r2dbc:h2:mem:///telemetry`, JDBC twin for Flyway) so the
service boots and self-tests with zero environment. That exact spelling is **pinned by
the delivered configuration test** (`ApplicationYmlConfigTest`), so it is a planned,
test-witnessed decision, not an oversight. A production deployment overrides at launch:

```bash
java -jar app.jar \
  --spring.r2dbc.url=r2dbc:pool:postgresql://db:5432/telemetry \
  --spring.flyway.url=jdbc:postgresql://db:5432/telemetry \
  --spring.flyway.user=... --spring.flyway.password=...
```

(The schema DDL is written in the PostgreSQL-compatible dialect; the embedded H2 runs
`MODE=PostgreSQL`.)

## Decision list (operator)

1. `ground_contact_time` and `respiration` have **no limits in the description** — the
   pipeline accepts them unbounded (`default -> true` in `ValidationService`). Supply
   boundaries → add config keys + one switch branch; the plan kept them as one honest
   open decision instead of inventing numbers.
2. **At-most-once inbound** (no dedup identity): identical retransmissions append
   duplicate revisions. If a client-supplied dedup key is preferred, the intake chain
   and the record identity must change together (plan rule (s)/(q) territory).
3. Embedded H2 as the boot default (see posture above) — flip to env-required
   placeholders only together with the frozen config test's pair.
