# Granularity
One component/contract = one task: one `path`, one exported type. Split above 1 layer, 3 collaborators, or 1 method group. Never tasks for packages/folders/modules; no invented requirements - trace to the spec.
# Observability is a runtime contract (design it before decomposing)
The strategy of EVERY executable context carries an `observability` object - UNCONDITIONALLY, whether or not the description asks for auditing, logging or visibility: the audit + step-log floor is operational hygiene, never a feature request, and emit refuses a strategy that lacks any surface of it. Abstract, no vendors: which STEP LOGS mark each boundary crossing (with the correlation key that ties them), which AUDIT TRAIL facts must survive as queryable records (actor, action, outcome, timestamp per regulated step), which METRICS answer the operational questions (what counts, what durations, with bounded tags). The active tech-stack skill names the concrete mechanisms.
THE FLOOR MUST COVER EVERY ACKNOWLEDGED OUTCOME (rule (u), 2026-11-16 PART III G4: a subscriber swallowed per-event errors after the service's FAILED audit - the failures were durable in the store and invisible in every counter, while the floor was "complete" because it only promised RECEIVED/VALIDATED/REORDERED/APPENDED): a floor is not a list of happy-path counts. (i) EVERY step log the strategy promises pairs with a metric (name or tag overlap) or an explicit `uncounted_steps` entry giving its reason - a boundary that is logged but never counted is operationally visible only to whoever queries the store by hand; (ii) every failure/drop/rejection/overflow outcome any contract SPILLS in tabled `semantics` pairs with a counting meter (a drop/error counter in the floor, claimed in the owning unit) or a declared `uncounted_failures` posture with its reason. Both layers are refused at emit. Mechanism naming stays with the tech-stack skill; the pairing law is stack-neutral.
It is not complete without an EXPORT SURFACE: the object must declare how those logs and records LEAVE the process in a machine-readable form - a named schema (structured event fields, not prose) written to a destination an external collector can consume (log-management tools such as Elasticsearch/Loki, metric scrapers such as Prometheus). The contract is written by the app; shipping/indexing is the platform's job, so the app NEVER hard-depends on the external tool: the default sink is a local append-only structured destination; a direct push endpoint only when the description names one, and then it needs the same offline-substitute treatment as an external database (the boot test passes without the tool running). The sink properties (format, destination, rolling) are operational values -> the CONFIG unit's literal keys.
Decompose it like domain logic - a duty without a unit is prose:
- an audit trail = PORT in domain/application (its record shape and emit method tabled in ast_hints) + ADAPTER in infrastructure +, when queryable, a MIGRATION owned by the database step;
- correlation = one middleware/filter unit at the entry boundary; if the strategy's own wording promises the correlation "via <mechanism>", installing that mechanism (dependency + enablement at wiring/boot) is a SCHEDULED DUTY of that unit or the wiring/config unit - rule (t): a promised mechanism nobody schedules is correlation by discipline, and one forgotten hand-pass loses the key silently;
- meters = the FLOOR NAMES tabled as machine fields, not prose: every meter a unit's contract
  touches sits in its `ast_hints.meters` as {name, duty} - duty `owns` on the exactly-one unit
  that registers the name (usually the metrics facade), duty `uses` on every unit that records
  or asserts it, citing the owner's spelling VERBATIM (rule (z)); never a scatter of raw logger
  calls: a business unit records contractual facts ONLY through planned ports, never ad-hoc text
  logs; the floor itself must be COMPLETE (rule (u)): every promised step log has its meter (or
  an `uncounted_steps` reason) and every contracted failure/drop outcome has its counter (or an
  `uncounted_failures` posture) - audited-but-uncounted failures are how a losing pipeline
  reports a healthy dashboard;
- a planned STEP LOG is an OWNED artifact, not vocabulary: every strategy `observability.step_logs` entry must be claimed VERBATIM in exactly one implementation unit's `observability.step_logs` field (that unit's coder puts one logger call at that boundary; that unit's tester asserts the captured event). Intent prose that merely mentions the same words claims nothing - an unowned step log is a log line that will never exist (2026-11-13: 5 planned, 0 owned, 0 in the delivered code, every gate green);
- levels/formats/sampling AND the sink's format/destination/rolling are operational values -> the CONFIG unit's literal keys, never code.
Every observability unit gets the same stage 1/2/3 triple, and its tests assert on CAPTURED structured surfaces (record contents, meter values, correlation fields), not on formatted strings - a log line nobody can assert on is a log line nobody can prove exists.
# DAG
Order: value objects -> aggregates -> outbound ports -> use cases -> inbound ports -> controllers -> configuration. `dependsOn` = direct only; cycles => reject. Siblings share or omit deps. Every unit = stage-1 test task + stage-2 code task + stage-3 refactor task - the planner emits all three (stage 3 shares stage 2's file, kind refactor, targetAgent agent-evaluator; nothing else creates it). The stage graph is law: stage 1 depends ONLY on stage 0 and on earlier units' stage-1 tasks; stage 2 on its own stage-1 task and on earlier units' stage-2 tasks (a pinned producer's code task); stage 3 on its own stage-2 task. A stage-1 task that dependsOn a stage-2 task inverts red-before-green and is refused at emit (2026-11-20 live: a carrier that omitted this law produced 19 stage-inverted edges in one draft - repaired, but in 21 edit calls that cost the session its budget).
# Payload contract (stage-1/2 tasks)
- `ast_hints` = THE API table: `package`; `implements` supertypes; `dependencies` [{type,task_id}] pinned to producers (a pin without one is a plan error; the producer must also be in `dependsOn`); `methods` [{signature,returns[,semantics}] spelling EVERY boundary method the unit provides - all implemented supertype methods + every accessor a pinned consumer touches; returns "" when none; value objects may list []. A member is INSTANCE unless its signature itself begins with `static`: prose like "read CorrelationContext.contextKey()" describes a call, not a binding - consumers that need to stub the member pin it as instance and take the type as a dependency. `semantics` is a note the tester MUST obey (nullability, initial-state encoding): REQUIRED on every entry when the unit's intent rejects null. Shared vocabulary is a machine field too: `meters` [{name,duty: owns|uses}] and `routes` [{method,path,duty: serves|uses}] - one unit owns/serves each literal, every other unit cites it VERBATIM, and a floor meter with no owner is refused (rule (z); 2026-11-19 R1/R2: while meter names and routes lived in prose, one board froze BOTH spellings of one meter and a controller test against a route its unit never served - pairs no payload satisfies). Property paths ride the same law: `config` [{path, kind: value|list|map, fields?}] - the unit whose record BINDS a path owns its shape (a list declares its element fields), the config-artifact unit cites path/kind/fields VERBATIM for every key its document seeds (rule (z5)). And a surface unit that pins a guard pins the guard's WORLD: every project product the guard's own table declares must sit in the surface unit's `dependencies` too, or no slice importing that chain can construct it (rule (z6)). Testers assert ONLY this table; the validator refuses implements-without-methods: an untabled collaborator makes consumers improvise contradictory signatures.
- `intent` carries the WHY and the literals, not the shape: target 40-80 words, hard ceiling 180 (refused
  at emit, planning only). Anything the table pins - a signature, a type, a collaborator - is not
  re-spelled in prose; prose that duplicates a table eventually disagrees with it and rule (e) refuses
  the pair. Keep what the gates demand: the security `spec_ref` + `capability` + mechanism, the config
  literals, both branches of a signal. Meter names and request paths are NEVER kept in prose - they
  are `ast_hints.meters` / `ast_hints.routes` (rule (z)), and a prose spelling the table omits is
  refused at emit.
- `tdd`: >=1 failing case per public method as given/when/then + test class path.
- `constraints`: layer rules + language/framework from the active tech-stack skill.
# Plan validity (emit-refused; seed-002 D1/D2/D3 roots + rerun F2/F4/F5/F9)
A duty the engine cannot execute is not a plan. At emit the validator refuses:
- (a) **Duty ownership**: every file artifact an intent names (config, migration, schema, manifest...) must be that unit's own `path` or another task's `path`. "Also provide <other file>" inside an intent is prose, not a plan - move the duty to the owning unit or schedule a unit for it.
- (b) **Config unit**: when any intent mentions externalized/operational values (framework config-property facility, runtime config file, "externalized config"), a CONFIG UNIT whose path targets the stack's runtime configuration artifact (its shape comes from the active tech-stack skill, e.g. `src/main/resources/application.yml`, `src/config.ts`, `src/settings.py`) MUST be scheduled carrying the seed's literal values in its intent. No config unit = every runtime default is fiction.
- (c) **Request-encoding alignment**: a pinned request-parameter type and the body shape the paired test intent mandates must agree - a streamed collection type binds with streamed-document bodies, an array/collection type with one-array bodies. The decoder can never satisfy both; refusing the pair at emit costs zero sessions.
- (d) **Nullability semantics**: when an intent rejects null on mandatory fields, the producing unit's `methods` entries must each carry `semantics` naming the initial-state encoding (a shipped constant like UNVALIDATED, or a nullable alternative). A null-intolerant value whose only purpose is to receive pre-validation data freezes two contradictory contracts (tester vs coder) with no owner able to fix it. The same holds for ARGUMENT-RANGE invariants - a claim like `revision (>=1)` in an intent is refused unless the constructor's table entry carries that bound and its sanctioned construction in `semantics`: consumer units' testers receive the collaborator TABLE, never this unit's prose, and a prose-only bound invites four foreign fixtures to fabricate the illegal literal and die on a frozen test they cannot edit (2026-11-16: `revision=0` fixtures against a `>= 1` record).
- (e) **Prose must not fight the table** (rerun F2 - the constructor-PROSE half of the drift the static-rule blocked at write time; the emit validator now refuses BOTH halves): an intent asserting an unconstructible shape ("private constructor", "utility class", "non-instantiable") cannot coexist with instance-bound members - either bind the members `static` in the table or open the constructor; and an intent that names a collaborator call in STATIC form (`Type.member(...)`) is refused when the pinned producer's table binds that member as an instance - spell the call against the INJECTED collaborator (`validator.validate(sample)`) or bind `static` in the producer's table. Two texts, one type: each side's tester writes what its own text says, and no payload can ever satisfy both shapes.
- (f) **Provider closure** (rerun F4): every type a table constructor INJECTS must have a named PROVIDER duty somewhere in the DAG - the producing unit registers itself (the duty spelled in its intent/table), or the wiring/configuration unit spells the provider duty for that exact type (@Bean factory / module export / registration). Injecting a type nobody provides crashes the context the moment the composition root can see it - or worse, boots green around an empty context (see (g)).
- (g) **Composition-root visibility** (rerun F3 + 13:45 slice half): the entry point's package must be an ancestor-or-self of EVERY component package AND of every context-discovering test package (@SpringBootTest-style slices search upwards and IGNORE scan directives - a directive waives only the component-scan half). Prefer the strategy's base package for the entry at scaffold time; the coverage duty otherwise belongs to the scaffold/wiring unit. The assembly gate now refuses both shapes structurally.
- (h) **Config-surface completeness** (rerun F5): a config-unit intent enumerates the FULL surface its paired test pins - when the test asserts several documents/sections (base + each profile), the intent must carry EVERY document with its activation key and literals. And every runtime reader the config ENABLES (a migration runner) must be given its own connection/URL keys in the SAME document or be explicitly disabled in the documents that must not run it: an enabled reader without a configured datasource silently migrates an auto-detected throwaway store while the app writes elsewhere. The duty set ALSO names the stack's test-profile ACTIVATION route (the tech-stack skill's mechanism, e.g. a test-scoped properties file written by the scaffold): documents nothing ever activates are fiction twice - once at boot, once in the coder that "fixes" it by poisoning a base default. Two more clauses, both from the 2026-11-19 R4 drain: SHAPE MIRROR - when another unit's record BINDS a path the document seeds, the config unit's `ast_hints.config` entry cites the binder's path, kind and fields VERBATIM (the binding record is the shape's only owner; a list of entries is indexed elements, never a scalar child key - the gate refuses the pair, rule (z5)); and BOOT-PATH PLACEHOLDERS - every `${VAR}` a bean constructor reads must be defaultable (`${VAR:}` with the refusal landing at boot where the plan can name it) or seeded in the document the test profile activates, because the scaffold's plain contextLoads smoke boots with no dynamic properties at all and an unresolvable placeholder makes the terminal gate permanently red.
- (i) **Stream egress** (rerun F9): every published stream port the plan exposes (subscriber-facing API) must either name its consumer unit in the DAG or state the boundary explicitly in the strategy (out-of-process subscribers; the in-tree sink is the contract surface). A stream nobody subscribes to drops (or overflow-counts) every event it publishes - a port without a consumer is prose about integration, not a plan for it.
- (j) **Step-log claim coverage** (2026-11-13 - the completeness failure the consistency gates structurally cannot see; 2026-11-20 V9 - the floor may be spelled as a flat list OR as the per-context mapping `{context: [logs]}` the strategy writes: BOTH shapes flatten before coverage is demanded, and a dict floor that skipped the check was the same 5-planned-0-owned story in new clothing): every execution-strategy `observability.step_logs` entry must be claimed VERBATIM (exact normalized text) by exactly one stage-2 unit's `observability.step_logs` field; an entry with no owner, a double claim, or a claim of an entry the strategy never planned is refused at emit with the offending string named. A strategy missing any floor surface (correlation_key, step_logs, audit_trail, metrics, export) is refused BEFORE claims are read - the floor is unconditional; only projects with no strategy file at all (legacy boards, unknown stacks) skip the whole rule.
- (k) **Consumer closure - rule reachability** (2026-11-16: a processing service implementing a core business RULE was constructed by the wiring unit but pinned by NOBODY as a collaborator - zero callers of its entry method and no subscriber to its output; every unit test green (they `new` the service directly), boot green (the component resolved) - and the rule never executed in the delivered pipeline. Provider closure (f) proves a type CAN be constructed; nothing proved it WILL BE USED): every stage-2 unit implementing a pipeline stage or a business rule the strategy enumerates must be REACHABLE from the entry-owning units through the pin graph - some other unit's `dependencies` pins it, or the wiring unit's intent names the ROUTING duty that places it on the data path (which consumer calls it, at which edge) - or the plan declares the boundary duty explaining the external caller in the strategy. A rule-owning service with zero consumers in the DAG is an island: connect it or refuse it.
- (l) **Shared literals have ONE owner** (2026-11-16: one "first revision number" fact spelled in four contracts with three different values (1 / 0 / >1), and one connection-string key read by two runtime readers that require different URL shapes - no environment can satisfy both): every literal used by >=2 units - a numeric origin, a wire/header key name, a meter or event name, a shared format - gets exactly ONE owning unit (usually an early value/constants unit) that spells it in its table/intent; consumers PIN that unit as a collaborator (or reference its named constant) - intents never re-spell the value. Two contracts spelling DIFFERENT values for the same named fact are a refused impossible pair: literals, like step logs, are owned, not shared by coincidence. Meter names and request paths are this law's MACHINE-CHECKED half - rule (z). Config half: a configuration value consumed by two runtime readers whose required forms differ (different protocols/schemes) must be exposed as DISTINCT keys, one per reader form, enumerated in the config unit's intent with its reader named; a single key feeding differently-shaped readers is refused.
- (m) **Both branches of a signalling return are contracted** (2026-11-16: an egress port method returned a success signal, the producer proved it false on overflow, the consumer's contract described only the happy path and ignored the return value - under burst the payload vanished while the entry point kept answering ACCEPTED; the false branch was never anyone's duty): whenever a pinned method's return is a decision/signal (boolean, result/enum, or their wrapped reactive/async forms), EVERY consuming unit's contract states both outcomes - `on_true` behavior AND `on_false` behavior (reject with an explicit status, apply backpressure, degrade, retry - an intent decision, never a fallback literal) - and the paired stage-1 test writes at least one case per branch. A signal whose false path nobody owns is a silent-drop seam: a returned false that no contract mentions is a false the coder will discard.
- (n) **One registration mechanism; declared validation must be activated** (2026-11-16: one component registered BOTH by a stereotype annotation on its class AND by a factory duty in the wiring unit - which definition wins is decided by container precedence, not by the plan; request DTOs carried declarative validation constraints no unit activated - decorative contract, and the seed's tag-don't-drop rule died at the API edge as a raw crash): every component product is registered by exactly ONE mechanism named in the DAG - either the composition/wiring unit's factory duty (its intent enumerates the exact types it produces) XOR the producing unit's self-registration duty (spelled in its own intent) - never both: double registration is a silent override on permissive runtimes and a boot failure on strict ones. And when a boundary DTO/table declares validation constraints, the ENTRY unit's contract names the enforcement mechanism (the stack skill's activation: parameter validation marker, schema enforcement, validation middleware) and the paired test proves a constraint violation is rejected AT THE BOUNDARY. Constraints nobody activates are prose.

- (o) **Persistence adapters are tested against the REAL substrate** (2026-11-16 second drain N1: the audit adapter's slice mocked the database client; NOT NULL, bounds and PK population stayed unproven - EVERY production audit write failed while 186 tests and a contextLoads boot stayed green). Whenever a stage-2 unit's contract executes SQL/DML against a schema, its paired stage-1 intent MUST name a real-substrate run: the embedded substitute EXECUTING THE ACTUAL MIGRATION DDL, asserting the durable row (valid AND constraint-violating cases). A mocked-client case may exist ONLY as an extra shape check beside it. Ask of every adapter: what proves the contract FITS THE SCHEMA, not just the call shape?
- (p) **Every inbound surface ships a request-path integration slice** (2026-11-16: unit tests build the use case with new; the smoke test loads a context without a request; nothing in the verified set ever crossed controller -> store -> row). A plan with an inbound HTTP/streaming adapter schedules ONE end-to-end slice: a stage-1 test task that drives the entry surface against the embedded substitute and asserts the durable effects, with its support unit. Per-stack mechanism (test client against the app, full context) comes from the active tech-stack skill; the duty is stack-neutral: the components must be proven to AGREE, not merely to exist. STATE IS A CONTRACT TOO (2026-11-19 R5): the slice shares one substitute across every case of its class, so its support-unit contract must NAME the isolation choice - each case seeds and asserts a UNIQUE identity, or asserts a RELATIVE delta against its own baseline, or the support provides a cleanup the cases run - and the slice intent says which; a bare global count on a shared store freezes JUnit method order into the contract (the seed-002 slice asserted `COUNT(*) == 1` after four sibling cases had written to the same row - red for every lawful implementation, unfixable by any of them).
- (q) **Retryable inbound over an append-only chain needs an idempotency duty** (2026-11-16 N4: a network retry is indistinguishable from a correction and mints a domain revision). Either a client-supplied dedup identity (key or natural business identity) is named in the receiving contracts, or the strategy declares at-most-once posture beside the inbound words. Server-minted random identity + revision chain + at-least-once transport without one of the two is a refused triangle.
- (r) **Migrations travel with the artifact** (2026-11-16 N8, and enforced at EMIT only): a config unit that enables a migration runner must name the runner location in its PACKAGED form (`classpath:` + the stack's packaged resources root), never a CWD-relative `filesystem:` path into the project tree - a jar started from another directory applies nothing and boots green over an empty schema. Portability is refused at plan time, NEVER re-demanded at the assembly gate: the config unit's frozen test pins the location string it was planned with, and a delivered-time second opinion demanding a different value orders the assembler to break a contract it must not touch (the 2026-11-16 T4 livelock).
- (s) **A dedup identity over a correcting chain is an identity-axis decision** (2026-11-16 PART III G2: rule (q) was HONORED - `UNIQUE(device_id, metric, t_device)` - and that is exactly how the seed's "corrections append new event revisions" died: a resent sample with the same identity but a CORRECTED value resolves as a duplicate no-op, silently, with the whole suite green; the strategy had left corrections handling as an Open question and the decomposition decided the question by omission): once the chain names a dedup identity AND the vocabulary speaks of corrections/backfills/supersession, the receiving contracts must STATE where the mutable payload (the value axis) lives relative to the identity - either the identity EXCLUDES the value and a named discriminator separates a retry (no-op) from a correction (revision appended): comparison, client-supplied version/sequence, correction flag - or the identity INCLUDES the value and every payload change is by definition a new revision, with the duplicate-payload case given its declared posture. The sentence is tabled where the identity is tabled, and BOTH resend classes become test duties of the receiving unit (same-packet -> no-op; same-identity-new-value -> revision). "Assumed handled as a correction" that no contract operationalizes is prose, not a decision; if the upstream boundary file carries the question as an Ambiguity/Open question, the strategy must carry the RESOLVED assumption - never the question plus a silent answer.
- (t) **A promised mechanism is a scheduled duty** (2026-11-16 PART III G3: the strategy promised correlation "propagated to log lines via context-propagation"; the decomposition planned manual key-passing and even tabled "no context-propagation library is used" in a unit intent - the plan and the strategy disagreed, the divergence lived only in prose, and every gate stayed green because nothing compares a promise to a duty): when the strategy's observability text names a mechanism ("... via <mechanism>"), some unit's intent must schedule the duty that INSTALLS it - declare the dependency and enable the mechanism at wiring/boot - using the mechanism token the strategy itself wrote (the concrete mechanism and its installation shape come from the active tech-stack skill; manual discipline is not a mechanism: a future line that forgets the hand-pass silently loses correlation and no test exists to catch it). A plan that will NOT install the mechanism must amend the strategy's promise to what it actually ships (and record the resolved assumption next to the question that produced it) BEFORE emitting - the emit gate refuses the mismatch, not the choice.
- (u) **No acknowledged outcome is unmetered** (PART III G4 - see the floor section above): every strategy step log pairs with a metric or an explicit `uncounted_steps` reason; every failure/drop/rejection/overflow outcome contracted in tabled `semantics` pairs with a counting meter in the floor, claimed by the owning unit, or a declared `uncounted_failures` posture. Audited-but-uncounted failures are how a losing pipeline reports a healthy dashboard.
- (v) **Config artifacts carry their KIND's format** (2026-11-16 delivered-tree finding: a runtime config document written as a flat list of dotted property keys - the properties form smuggled into a structured document; boot-green and test-green because loaders flatten both spellings, but the file stopped being the format its kind defines, and a human reader reported it as a bug): the plan tables KEY/VALUE operational facts as SEMANTIC PROPERTY PATHS - the dotted spelling is the lookup name, NEVER the file layout; the serialized artifact must use the NATIVE form of its file kind as spelled by the active tech-stack skill (structured-document kinds nest; flat key-value kinds spell dotted keys with their assignment token). A config-unit intent that DEMANDS an artifact be written in another kind's syntax ("flat dotted-key style" onto a structured document) is off-plan; the emit validator cannot see the file text, so the machine half lives at the ASSEMBLY gate - where the fixer (the assembler) can still act and the fix is provably safe: re-serialization carries NO values (the runtime loader flattens nested and flat spellings to identical property paths), and the tester contract pins config oracles to that loader, so no frozen test can see the change. This is the deliberate, argued exception to the (r) doctrine "never relitigate at a delivered gate": (r) refused a delivered second opinion because it demanded a different VALUE against a pinned string; (v) demands a different SHAPE, values and tests untouched - format is fixable twice: at plan time by the intent's silence (just table the pairs), at delivered time by re-serialization.
- (w) **A test task owns a test file** (2026-11-17 drain: the architect emitted EVERY stage-1 task with the production file as its `path`; the tester - contractually bound to write only at `path` - wrote `@Test` classes into `src/main/java`, whose test-scoped imports (JUnit/AssertJ/Mockito/reactor-test) are invisible to the main classpath; the import-closure guard stopped the drain at the first red close-out instead of billing a hundred sessions against it): a stage-1 `path` is the TEST artifact the tester creates - a separate file from the unit under test, NEVER the paired stage-2 task's path (stage 3 may share stage 2's file: its refactor targets the implementation). One file cannot hold both the frozen test and the unit woven over it; every stack keeps its test artifacts in files the production classpath never compiles.
- (x) **A mapped handler must name the registration its framework can execute** (2026-11-17 drain: the controller's intent pinned "no scanning-registration annotation: it is registered only by the wiring factory" - WebFlux's handler mapping accepts ONLY classes carrying the controller annotation (verified against the framework bytecode), so the factory bean was constructed, boot was green, and every request to the endpoint answered 404; the e2e slice caught it, the per-unit gates could not): an inbound handler unit declares ONE mechanism - the marker the active tech-stack skill names on its own class (the wiring unit then supplies its collaborators, not a second registration), or a functional router bean owned by the wiring unit. An intent that FORBIDS the marker while assigning registration solely to the factory is the impossible pair the emit gate refuses for the planned language.
- (y) **A security duty is claimed, implemented, reachable and asserted** (2026-11-18 probe: a plan whose every duty was CLAIMED still shipped an inbound entry unit with no guard on its path - the claim lived in an island unit the entry never pinned, so the surface was implemented, gated and closed before its predicate existed, and every per-unit gate stayed green). When `blackboard/complete/security-spec-<slug>.json` exists, each of its `duties` is discharged inside a unit object of the ONE draft array by spelling BOTH its `spec_ref` token and its `capability` token VERBATIM, beside the mechanism chosen for it (the active tech-stack skill's marker, filter, guard, provider or config key - the spec deliberately names none). Coverage alone is not placement: (y1) the claim sits on the stage-2 unit that ENFORCES it - a tester's or evaluator's intent implements nothing; (y2) REACH - the strategy's `surfaces[].name` is written into the intent of the unit that IS that surface, and that unit pins the enforcing unit in its collaborator table with its id in `dependsOn`, or the predicate is a tabled method on the unit that performs the lookup itself; (y3) ASSERTION AT THE SURFACE - that entry unit's paired stage-1 intent carries the row id AND the row's `test_duty` CROSS-OWNER case (a valid identifier owned by someone else, refused). The drain orders units only by `dependsOn` and testers assert only against pinned tables, so an unwired guard is invisible to the frozen pair that would have caught it: a role check that still fetches another tenant's row by id is the IDOR the spec forbids.
- (z) **A shared literal has one tabled owner and one verbatim spelling** (2026-11-19 - the R1/R2 roots of the 2026-11-18 drain, the class rule (l) named but structure could not see): every METER NAME a contract touches is tabled in `ast_hints.meters` as {name, duty} - duty `owns` on exactly ONE unit (the facade/instrument that registers it), `uses` on every unit that records or asserts it, citing the owner's spelling VERBATIM; every REQUEST PATH is tabled in `ast_hints.routes` as {method, path, duty} - `serves` on exactly ONE inbound unit, `uses` on the guards, callers and slices driving it. A floor meter with no owner, an owned name off the floor, a `uses` no owner answers (the near-miss spelling is named: `telemetry.validation.failed` is NOT `telemetry.samples.validation_failed`), a route served twice or cited unserved, a literal spelled in a unit's intent or `semantics` while its own table omits it, and a unit whose T1 and T2 carry different (not IDENTICAL) tables are ALL refused at emit. The drain's frozen pair writes both sides from these tables - one board shipped the consumer test pinned to one meter spelling and the facade's own (regenerated) test pinned the other: no payload can satisfy both, and the coder burned 3/3 sessions on the contradiction while every per-unit gate stayed green; the same shape froze a controller test posting `/ingress/packets` against a chain, an intent and a slice all spelling `/telemetry/ingress`. The law extends to two more literals and one visibility trap: **(z5) property paths** - every seeded or read path is tabled in `ast_hints.config` as {path, kind: value|list|map, fields?}, the unit whose record BINDS the path owns its shape and every other unit (the config writer above all) cites path, kind and fields VERBATIM; two kinds for one path, differing element fields, or a dotted child under a tabled list are the impossible pairs the gate refuses (2026-11-19 R4: the record declared `devices` as a LIST of (id, secret-hash, scope) while the config unit's own contract seeded `devices.secret-hash` as a scalar - a file cannot bind both, the credential store booted empty, and the scaffold's contextLoads stayed red forever). **(z6) a guard's world is visible to the surface it guards** - the surface unit that pins a guard must also pin every project product the guard's own table declares (dependencies and method parameters): a test slice that imports the chain builds it from the container, and a concrete bean the plan's wiring law keeps in the factory alone is NoSuchBeanDefinition at every slice boot (R3: the streaming controller's test imported the chain its sibling had correctly doubled - one tabled collaborator decided which unit could ever run).

# Emission (a token budget, not a style rule)
ONE JSON array **per bounded context** (`/tmp/tasks/<slug>-<context>.json`), ALL files passed to a
**single** `python3 <runner> --emit f1 f2 ...`: the batch is still validated as a whole - cross-context
pins, provider closure and the security reach law each see every file - while no one output turn has to
carry a whole domain (measured: one 57-task plan = 23,585 tokens of JSON; the largest context here is
~8k; a real session's biggest single output turn hit 40,442 tokens). On rejection, **edit** the task
objects the errors name and re-emit the same files once: a full-plan rewrite costs 10-30k output tokens
for a fix worth a few hundred. Never write `blackboard/queue` directly; never reuse ids.
