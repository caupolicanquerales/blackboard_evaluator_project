# PulseStream Engine

Reactive, non-blocking telemetry ingestion and backfill-reordering service for 1 Hz
time-series from IoT edge devices, bike computers and smart wearables. Generated by
the Blackboard pipeline from `seed/002_description.md` (third drain — 32 units,
102 tasks, **258/258 tests**, integration proven by its own request-path e2e slice).

**Status: deployable ingestion service.** Known edges (G1–G4) and full evidence:
`PROJECT-INSPECTION-2026-11-16.md` PART III (repo root).

| | |
|---|---|
| Runtime | Java 21, Spring Boot 3.5.16, WebFlux (Project Reactor) — zero blocking calls on the request path |
| Persistence | R2DBC + Flyway, migrations **applied from the packaged classpath** via a `FlywayConfigurationCustomizer` — the jar is CWD-independent (but see G1 below) |
| Databases | PostgreSQL in production (env placeholders); H2 in the `test` profile only |
| Entry | `com.blackboard.telemetry.TelemetryIngestionProcessingApplication` (ancestor of all packages — slice discovery and component scan need no directives) |

## What it does (business rules → implementation)

1. **Ingestion** — `POST /api/v1/telemetry/packets` accepts one JSON packet carrying a
   list of samples; every sample is validated against physical boundaries
   (heart rate 30–240, power 0–2500, cadence 0–220, swim pace > 45 s/100 m via a
   one-sided `minExclusive` bound; ranges the description leaves unspecified —
   ground-contact time, respiration, swim stroke — are declared `enabled: false`,
   never invented). Invalid samples are tagged `VALIDATION_FAILED` and **stored
   anyway** — a validation failure is data, never a rejection.
2. **Append-only history** — every accepted sample becomes an immutable
   `telemetry_sample` row; corrections attach as rows in `event_revision`
   (`revision_no` chain enforced by `UNIQUE (sample_id, revision_no)`, reason ∈
   `BACKFILL` / `CORRECTION`). The initial validation state is an honest third
   enum value: `ValidationStatus{UNVALIDATED, VALID, VALIDATION_FAILED}`.
3. **Reordering by device time** (`ReorderHistoryService.stage`), per sample, three
   branches:
   * **later than the window** (`tIngress − tDevice > reorder-window`) → append a
     `BACKFILL` revision, broadcast `REVISION_APPENDED`, audit;
   * **inside the window but older than the device's newest known sample** → reorder:
     meter `telemetry.samples.reordered`, broadcast `SAMPLE_BACKFILLED`
     (log `sample reordered within backfill window`);
   * **otherwise** → register in the bounded window
     (`findWindow` over `reorder-buffer-capacity` rows), broadcast `WINDOW_BUFFERED`.
4. **Backpressure & idempotency** — bounded Reactor sinks throughout: the
   ingestion→history stream is `Sinks.many().multicast().onBackpressureBuffer(
   validated-stream-capacity, false)` (autoCancel off) with a **deadline-bounded**
   emit retry (`emit-retry-timeout`), and the downstream broadcast is
   `Sinks.many().replay().limit(broadcast-capacity)` with `emitNext(busyLooping(
   timeout))`; a contended emit that exhausts its deadline surfaces as an error →
   FAILED audit + `503`, never a silent drop or unbounded spin. Resubmission of the
   same natural identity `UNIQUE (device_id, metric, t_device)` is caught as a
   `DataIntegrityViolationException` and becomes a **silent no-op — the client still
   receives `202`, no new row, no revision**: a network retry can never mint a
   spurious revision (pinned by `PipelineEndToEndTest`).
5. **Observability floor** — every boundary crossing writes an `audit_trail` row
   (actor / action / outcome / occurred_at / correlation_id); all seven promised
   step logs are emitted (verified `NONE` missing); counters/timers per outcome:
   `telemetry.packets.received{source_kind}`,
   `telemetry.samples.validated{metric,status}`,
   `telemetry.samples.reordered{metric}`,
   `telemetry.revisions.appended{reason}`,
   `telemetry.pipeline.latency{stage=validate|history}`.
   ECS-structured file logging with rolling (10 MB × 7), Actuator `health` +
   `metrics` exposed. Correlation: `CorrelationWebFilter` accepts a client
   `X-Request-Id` (≤ 128 chars, `[A-Za-z0-9._-]+`) or mints a UUID, **echoes it on
   the response headers**, and writes it into the Reactor Context, where
   `CorrelationContext.current()` reads it for every log line and audit row.

## API

`POST /api/v1/telemetry/packets` — a **single JSON object** (`consumes: application/json`):
`{deviceId, sourceKind, samples: [{metric, tDeviceEpochMillis, value}, …]}`, validated
with Bean Validation (`@NotBlank` / `@NotEmpty` / `@Valid`).

| outcome | status |
|---|---|
| packet accepted (valid, invalid-tagged, or duplicate) | `202 Accepted` — always; validation failures are stored inside, not rejected, and a duplicate natural identity is a no-op that still answers 202 |
| malformed body, blank identity, unknown `sourceKind`/`metric` enum literal | `400` (`@Valid` rejection, or `ResponseStatusException(BAD_REQUEST)` from the DTO's `toDomain`) |
| sustained emit contention past the deadline (`IllegalStateException`) | `503 SERVICE_UNAVAILABLE` (mapped in the controller's `onErrorMap`) |

```bash
curl -s -X POST http://localhost:8080/api/v1/telemetry/packets \
  -H 'Content-Type: application/json' \
  -H 'X-Request-Id: demo-001' \
  -d '{
    "deviceId": "rider-watch-42",
    "sourceKind": "SMART_WEARABLE",
    "samples": [
      {"metric": "HEART_RATE", "tDeviceEpochMillis": 1763280000000, "value": 142.0},
      {"metric": "POWER",      "tDeviceEpochMillis": 1763280001000, "value": 310.0},
      {"metric": "HEART_RATE", "tDeviceEpochMillis": 1763280002000, "value": 999.0}
    ]}'
```

* The third sample breaks the 30–240 bound → stored tagged `VALIDATION_FAILED`,
  metered `telemetry.samples.validated{metric=HEART_RATE,status=VALIDATION_FAILED}`,
  audited — **not** dropped, request still `202`.
* Resending the same packet: same natural key → one row, no revision, still `202`
  (the e2e slice asserts exactly this).
* `sourceKind ∈ {EDGE_DEVICE, BIKE_COMPUTER, SMART_WEARABLE}`;
  `metric ∈ {HEART_RATE, POWER, CADENCE, SWIM_PACE, GROUND_CONTACT_TIME, RESPIRATION, SWIM_STROKE}`.
* The `X-Request-Id` is echoed on the response and carried through audits and the
  reorder pipeline.

## Configuration (`telemetry.*`)

| key | value | meaning |
|---|---|---|
| `reorder-window` | `PT60S` | backfill watermark window (re-index by device time) |
| `reorder-buffer-capacity` | `4096` | bound on the windowed sample read |
| `validated-stream-capacity` | `1024` | ingestion→history multicast sink bound |
| `broadcast-capacity` | `1024` | downstream replay publisher bound |
| `emit-retry-timeout` | `PT0.1S` | deadline for contended emits (bounded, never spin forever) |
| `boundaries[0..6]` | seed ranges | per-metric `{metric,min,max,min-exclusive,enabled}`; `SWIM_PACE` uses `min-exclusive: true`, the three unspecified ranges ship `enabled: false` |

Datasources/credentials arrive **only** via `TELEMETRY_R2DBC_URL`,
`TELEMETRY_JDBC_URL`, `TELEMETRY_DB_USER`, `TELEMETRY_DB_PASSWORD` (no defaults in
the base document). Logging and actuator keys are in `application.yml` (ECS file
appender, `health,metrics` exposure).

## Test surface

33 test classes / **258 tests, 0 failures, 0 errors**: per-unit contracts on the
tabled API; R2DBC slices that execute the **actual V1/V2 migration DDL** on H2 via
`ConnectionFactories` (the persistence substrate is proven, not mocked); and the
request-path e2e slice (`PipelineEndToEndTest`, 8/8) that drives the live HTTP entry
against the migrated schema and asserts durable VALID rows, retained
VALIDATION_FAILED rows, idempotent resubmission (one row, no revision) and the
downstream broadcast — the integration proof unit gates structurally cannot produce.

## Known limitations (from `PROJECT-INSPECTION-2026-11-16.md` PART III)

* **G1** documented-vs-effective flyway location (see note above) — cannot recur in
  newly generated plans (plan rule (r) shipped).
* **G2** a resubmitted sample with the same identity `(device_id, metric, t_device)`
  but a **changed value** is a silent no-op (unique-constraint dedup), not a
  correction revision; correction semantics along the value axis remain an open
  operator decision.
* **G3** correlation reaches log lines as explicit `requestId={}` arguments — there
  is no MDC/`context-propagation` bridge, so it is discipline, not mechanism.
* **G4** dropped broadcasts are audited (FAILED rows) but not metered — a
  `telemetry.pipeline.dropped{stage}` counter would close the observability loop.
* Cosmetic: `HELP.md` remains, and the legacy package directory
  `telemetry_ingestion_processing/` — emptied in `src/main` when T4 moved the entry
  class to the ancestor package — still holds the boot smoke test under `src/test`.
