# Purpose
Boundary slices => validated context maps, one per slice in `blackboard/context-map/`. Analysis only; no code/APIs/schemas. Discovery slices must exist and parse (reader tool); missing/invalid => stop+report; never invent contexts.
# Workflow
1. Confirm inputs: each context has responsibility, language, owned invariants, source of truth. Invariant with 0 or 2 owners => return to discovery.
2. Interactions per pair: what crosses; initiator; up/downstream; what never leaks; eventual vs immediate. Three mechanisms, never conflated: asynchronous EVENT (publishes/consumes), synchronous QUERY (a slice `reads` entry), synchronous COMMAND (a write inside another context's ongoing flow). Nothing crosses => separate ways.
3. Relationships (`relationship` EXACT enum; choose by condition, not fashion; direction upstream->downstream): **direction follows supply, not the caller** - upstream = whoever OWNS the data/capability being used, downstream = whoever consumes it. A synchronous query or command is INITIATED by the consumer, and that never flips the edge: the supplier stays upstream, the initiator is named in `exchanged_information`/flow notes ("called by X during Y"), never by swapping the pair. External systems orient the same way: a provider you call to get an answer (completion, summarization, a tool result) SUPPLIES that answer - `external` is the upstream and your context the downstream, with the Anticorruption layer translating its model on your side. Only when you expose YOUR contract for the outside world to consume does `external` sit downstream (Open host service / published language). The writer refuses the two contradictory shapes (ACL pointing at external; external as an open host upstream) - do not meet it there.
   Partnership - co-evolve (coupling risk). Shared kernel - minimal explicit shared model (keep tiny, name it). Customer-supplier - negotiated downstream needs. Conformist - downstream adopts upstream model (loses freedom). Anticorruption layer - downstream translates foreign model (protects, costs maintenance). Open host service / published language - stable versioned contract for many consumers. Separate ways - nothing meaningful crosses.
4. Flows: mechanism (event | query | command), payload concept, initiator, consumers, consistency (transactional|eventual|immediate), failure posture (retry/idempotency/compensation). **Read-after-event shape**: when a context synchronously reads state that is refreshed asynchronously - by its own or another's events - the read can lag the write; the flow must then state the staleness posture the design commits to: bounded-lag tolerance (and what a stale answer costs), synchronous refresh before the initiating write is acknowledged, or serialization of the next read until the refresh lands. An unstated posture becomes an ordering guarantee the task planner invents silently (2026-11-26 live: a fan-out-fed window read back-to-back by the same caller - the lag was real, the posture was blank).
5. Protections: translate where models diverge; name what may cross (events, published language) and what may not (internals).
6. Wiring closure - a flag is not a fix: every event a context `publishes` ends with a consumer or with an ADJUDICATED open decision, never with a bare flag as its only outcome. A publish nobody consumes and an invariant that needs data another context produces ("every X is stored" while X originates elsewhere) are the same hole seen from both shores - close it from the slices' own words:
   a) WIRED: the context whose invariant/responsibility/source-of-truth demands that payload is its consumer. Record the edge in `context_map` and the flow in `cross_boundary_flows` with the MECHANISM named (async event, eventual; or synchronous inbound command, immediate), and quote the deciding slice phrase in the flow notes. This is reading what the slices already state, not inventing a context; the slice files stay untouched - the map carries the resolution.
   b) ADJUDICATED OPEN: no slice sentence decides the consumer. Then state the decision as planning-blocking, with BOTH candidate wirings named (which context subscribes to the event vs which caller issues a direct command) and what each choice commits downstream. An unadjudicated wiring is inherited as a silent guess by the task planner (2026-11-26 live: an unmatched publish shipped as a note-flag and the write path into the append-only log stayed a guess).
   Also validate: a slice's `reads` entries (synchronous queries, not events) map as immediate request/response flows - never as invented event pairs; unmatched terms flagged ambiguous; no unnamed coupling cycles.
# Output
`context-map-<slug>.json` payload keys ONLY: schema_version "1.0", report_type "context-map", metadata{generated_at, agent, source_report "blackboard/domain"}, context_map[{upstream, downstream, relationship, direction, exchanged_information, boundary_protection}], cross_boundary_flows[{business_process, contexts_involved, consistency_expectation, notes?}]. Context names exact or "external"; required context_map when >1 context. No other top-level keys. Persist via the writer script; `--emit-template context-map` prints the exact skeleton.
