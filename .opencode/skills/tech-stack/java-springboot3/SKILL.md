# Stack facts
**Java 21 default**: when the business description names a Java version, THAT version is the pin and is written VERBATIM (e.g. a seed saying "Java 21" yields language "Java 21"); when it names none, the default is **Java 21 (LTS)** - never 17, never a tool default (Spring Initializr's own default is a trap, not a decision). "17+" is the Boot-3 MINIMUM, never an emitted version: strategy, scaffold intent and `pom.xml <java.version>` must all carry one EXACT number. Spring Boot 3.x - keep existing build/versions. `jakarta.*` only, never `javax.*`. Web: spring-boot-starter-web OR webflux (reactive = Mono/Flux everywhere, no blocking adapters). Persistence: spring-boot-starter-data-r2dbc (reactive, non-blocking - the blackboard default) or data-jpa; Flyway for migrations; embedded H2 ONLY for boot/compile verification, never production wiring - and NEVER in the BASE document, neither as a literal default nor as a `${VAR:r2dbc:h2://...}` fallback default: base connection values are BARE `${...}` placeholders (or the production database the description names), and the substitute reaches the boot ONLY through the test-profile document + activation route (Build/verify: a test-scoped properties file). When a boot goes green only by weakening a base default, the missing piece is the ACTIVATION file, never the default. Test: spring-boot-starter-test, reactor-test; Mockito allowed; NO unmanaged network at build.
# Language conventions (planning)
Constructor injection, final fields; records for DTOs/commands/queries; interfaces (ports) + thin adapters; validation at boundaries (@Valid + ProblemDetail mapping); @Transactional at the use-case boundary; no business logic in controllers; no entities in responses. EVERY collaborator type a table constructor injects has exactly ONE named provider: the class's own stereotype (its producing unit states the registration duty) or a `@Bean` factory in the wiring configuration unit - an injected-but-unprovided type is a plan error the wiring unit must answer (seed-002 rerun F4). HANDLER REGISTRATION (WebFlux): `RequestMappingHandlerMapping.isHandler` accepts ONLY classes annotated `@Controller` - no `@RequestMapping` fallback (verified against the framework bytecode, 2026-11-17): an annotation-free POJO produced by a `@Bean` factory boots green, the bean exists, and every request to its own endpoint answers 404. So an annotated controller carries its marker and self-registers (the wiring unit supplies its collaborators, never a second `@Bean` of it); a plan that wants factory-only routing schedules a functional `RouterFunction` bean instead - the emit gate refuses the impossible pair. COMPOSITION-ROOT PLACEMENT: the `@SpringBootApplication` class must sit AT the base package every component lives under - the Initializr nests it one level deeper (`<base>.<artifact_under>`): a root in a subpackage scans only its own subtree (the real beans never register) and `@SpringBootTest` in any sibling package dies on the upward config search; the scaffold skill's placement check relocates it.
# Layout
base package = strategy `module_layout.base_package`; packages by FEATURE within layer; interfaces in domain/application, JPA/R2DBC entities + adapters under infrastructure; config in shared. The @SpringBootApplication entry point lives IN the strategy base package or above every component package - Initializr's default groupId package is NEVER a decision: when the scaffold places it elsewhere, the coverage directive (`scanBasePackages = "<base_package>"`) is the wiring unit's own duty, spelled in its intent (seed-002 rerun F3: the boot gate refuses a root that cannot see its code).
# Build/verify
Wrapper `./mvnw` only; compile `./mvnw -q compile`; test scoped `./mvnw -q -Dtest=<Class> test`. Maven offline-friendly pins; no plugin network surprises. Scaffold rule: Initializr's OWN defaults are never decisions - `bootVersion` and `javaVersion` are always sent from the strategy pins (a "Spring Boot 3" plan on a Boot 4 pom is off-plan), and the generated pom must carry `spring-boot-starter-test` + `reactor-test` (reactive plans): missing test artifacts are a classpath hole no coder can survive. TEST-PROFILE ACTIVATION is a scaffold duty, not a coder trick: `src/test/resources/application.properties` carrying `spring.profiles.active=test` is what makes the boot test read the profiled YAML document - it is a runtime CONFIG resource (no test code), it must exist from stage 0, and it is the ONLY sanctioned route by which embedded H2 reaches a boot (base-document defaults stay production). The TEST-RUN TIMEOUT guardrail is likewise a scaffold duty with a sanctioned tool: the surefire `forkedProcessTimeoutInSeconds` setting is written by the scaffold skill's script flag (`--surefire-timeout <seconds>`) - never a hand edit, never a coder payload, and never a reason to leave the task path without a pom. CONFIG FORMAT FOLLOWS THE ARTIFACT KIND (corrected 2026-11-17; the old "flat dotted keys are canonical" clause was WRONG in its own reasoning and was the seed of a format bug report): `application.yml`/`*.yaml` carry YAML's NATIVE NESTED FORM - maps nest by indentation, list-of-objects config (`telemetry.boundaries`) is a YAML SEQUENCE, never `key[0]` pseudo-lines; `application.properties`/`*.properties` carry the FLAT `key=value` FORM. Dotted paths like `spring.r2dbc.url` are the SEMANTIC property names - the lookup keys the plan tables and the loader flattens FROM a nested document - not a file layout: writing flattened dotted keys into a structured document is the properties vocabulary smuggled into YAML (valid to the binder, unreadable to a reviewer, and the exact complaint the 2026-11-16 artifact drew). A key whose LEAF segment contains dots (`logging.level.com.<pkg>`) stays ONE key at its nesting level - YAML mapping keys may contain dots; this myth was the old clause's only "reason" and it is false. `YamlPropertySourceLoader` flattens nested and flat spellings to IDENTICAL property paths, so binding and loader-based tests cannot tell them apart - which is precisely why the format is fixable at delivered time WITHOUT touching a test, while values are not (rule (r)'s frozen-string doctrine stays untouched: this probe demands re-serialization only, never a value edit, never a test edit). Never MIX conventions inside one document (the mix is where duplicate-key collisions hide), and never write `key=value` lines into a YAML document (they are scalar noise no binder reads).
# Observability & audit design (the concrete side of the strategy's `observability` object)
Logs: SLF4J facade only (`org.slf4j`), one `private static final Logger` per class that OWNS a planned step - the steps a class owns are exactly the entries VERBATIM in its task's `observability.step_logs` claim: a claimed step gets one logger call at that boundary, an unclaimed class adds no logger; never `System.out`/`printStackTrace`; never a contract fact emitted as scattered ad-hoc text - business units record facts through the planned audit port, operational detail through the logger at the boundaries the strategy names. Machine-readable output is a CONFIG decision: `logging.structured.format.console=ecs|logstash|gelf` (Boot >= 3.4 built-in) or `logback-spring.xml` + JSON encoder below that - keys and levels live in the config unit's application.yml, never in code. REACTIVE MDC TRUTH: thread-local MDC does NOT survive event-loop hops - a plan that wants the correlation id on LOG lines must name the context-propagation mechanism (micrometer `context-propagation` + `Hooks.enableAutomaticContextPropagation()`, declared as a duty of the correlation unit or the wiring unit) or accept that correlation lives ONLY in the Reactor Context and the audit surface; never let a coder "fix" log correlation with a bare `MDC.put` in a WebFilter and call it done (the line loses the id at the first hop and every gate still passes).
Export for external tools (the strategy's `observability.export`) - Elasticsearch-consumable by construction: on Boot >= 3.4 set the FILE sink to Elastic Common Schema in the config unit's application.yml - `logging.file.name: logs/<slug>.log`, `logging.structured.format.file: ecs`, `logging.logback.rollingpolicy.max-file-size/max-history` - ECS JSON lines are ingested verbatim by Elastic Agent/Filebeat with zero app code; Boot < 3.4 equivalent: `logback-spring.xml` RollingFileAppender + `logstash-logback-encoder` (`LogstashEncoder` or ECS provider). Console may stay plain-text for dev; the FILE is the contract surface. Direct-to-cluster appenders (`ElasticsearchAppender`, OTLP push) ONLY when the description names the endpoint, and then the offline rule holds: the boot test must pass with the cluster absent (appender disabled under the test profile). The strategy names the schema (ecs/logstash/gelf); the config unit carries the literal keys; nothing in src/main/java constructs the sink.
Correlation: one interface-layer filter unit. WebFlux: a `WebFilter` that generates/adopts a `requestId`, writes it with `contextWrite` and surfaces it in logs via micrometer context-propagation (or passes it EXPLICITLY into audit records - do not trust MDC across threads in reactive chains); MVC: `OncePerRequestFilter` + MDC is fine. The correlation key is a field of the audit record, not only a log field.
Audit trail: application/domain PORT (e.g. `AuditTrail.record(AuditEntry entry)`) with the entry shape tabled in ast_hints (actor, action, outcome, timestamp, correlationId - and the initial-state/nullability `semantics` of every field); infrastructure adapter persists to an append-only `audit_trail` table via Flyway expand-only migration (the migration is the database step's unit); when the invariant demands the fact survive with the change, the audit write joins the same transaction/reactive chain, otherwise best-effort async is stated in the intent.
Metrics: Micrometer through `spring-boot-starter-actuator` in the scaffold intent (+ `micrometer-registry-prometheus` only if the description asks for a scrape endpoint). Inject `MeterRegistry`; `Counter`/`Timer` with the EXACT names the strategy tabled; bounded tags only (statuses, kinds - NEVER entity ids like deviceId: unbounded cardinality). Meter name + meaning live in the consuming unit's ast_hints so the test can assert the value.
Testable surfaces (what the tester red-tests against): captured `ILoggingEvent`s via a Logback `ListAppender` attached to the unit's logger (assert marker/MDC/structured fields, not the formatted string); counts/timers via a `SimpleMeterRegistry` injected into the unit; audit records via the port's test fake or ArgumentCaptor; never assertions on human-readable text or locale-dependent formatting. MOCKABILITY LAW: `sealed` and `final`-on-interface are incompatible with `@Mock` - Mockito cannot stub a closed type. A unit must not close (seal/finalize) a type that any other unit's table pins as a collaborator, and an evaluator must never seal a surface as a tidy-up: the consumer's frozen stub-based tests die and their owner can edit neither the test nor the foreign modifier. Model a closed event hierarchy with the records themselves in tests (construct real instances) ONLY when the plan says so; when a type is stubbed anywhere, keep it open.
# Prohibitions (tasks must never specify these)
ddl-auto=update outside tests; secrets in config; Thread.sleep/blocking IO in request paths; unbounded buffers; hardcoded timeouts (bind to config keys); Lombok unless already present. Embedded-H2 harnesses must survive PostgreSQL-dialect identifiers: URL option `NON_KEYWORDS=VALUE` (H2 reserves `value`; telemetry-shaped schemas hit this live) or quote reserved columns; and PostgreSQL-dialect TYPES too: migration DDL is executed VERBATIM by slice tests against plain H2 (no compatibility mode - the URL is frozen inside the test), so a vendor type there kills the unit and no coder payload can repair it (seed-002 2026-11-16: `TIMESTAMPTZ` - 15 errors, 2 units quarantined; `TIMESTAMP WITH TIME ZONE` is the portable spelling that is equally valid on PostgreSQL); test-side schema comes from the real migration files' content, never retyped DDL that drifts from it.
# Naming for DDL/migrations
Flyway: `V<n>__snake_case_description.sql`, PostgreSQL dialect, snake_case tables/columns, `version` integer column for aggregate roots. Migration RUNNER config uses the Spring namespace in the file Spring loads: `spring.flyway.locations` (+`enabled`) inside `src/main/resources/application.yml` - never bare `flyway.*` keys in a stray profile file no runtime imports. ONE canonical script directory, and it must TRAVEL WITH THE ARTIFACT: `spring.flyway.locations: classpath:db/migration` with the scripts under `src/main/resources/db/migration` - the packaged jar is self-contained, while a CWD-relative `filesystem:db/migrations` boots green over an EMPTY schema when `java -jar` runs from anywhere else (2026-11-16 second drain N8; the assembly gate now refuses filesystem: locations that point inside the project). Slice tests read the SAME packaged resource from the classpath, so schema-under-test and schema-deployed cannot diverge; a root `db/migrations/` copy is only legitimate as an explicit deployment artifact OUTSIDE the tree, with the locations token pointing at it and a NAMED copy duty. An ENABLED runner must share its document with a datasource URL for the database the runtime actually writes (a JDBC url key beside the R2DBC one, from a DISTINCT environment placeholder - `${X_JDBC_URL}` vs `${X_R2DBC_URL}` - NEVER one variable feeding two URL schemes: no deployment can satisfy both and the fiction is invisible at boot): flyway-enabled + no datasource config silently migrates the auto-detected embedded store while R2DBC writes elsewhere - the production schema stays fiction (seed-002 rerun F5 adjacent). Multi-document artifacts: when the paired test asserts several documents (base + profile), the config unit emits EVERY document - e.g. a `---` test profile activating H2 (`spring.r2dbc.url: r2dbc:h2:mem:///...`) with `spring.flyway.enabled: false`; a single-document file can never satisfy a two-document assertion.

# Reactive substrate laws (seed-002 second drain N2/N5: a green suite hid both)
- FAN-OUT SINK LIFECYCLE: a `Sinks.many().multicast()` that feeds a `retryWhen`
  consumer or external (re)subscribers MUST be built as
  `onBackpressureBuffer(capacity, false)` - autoCancel=true terminates the sink when
  the last subscription goes away, and every later emit FAILS TERMINATED: one window
  overflow or one external subscriber disconnect permanently kills ingestion while
  the boot test smiles. The 2-arg form is the default choice in this repo.
- BOUNDED EMIT RETRY: never `do { tryEmitNext } while (FAIL_NON_SERIALIZED)` - an
  unbounded busy-spin on an event-loop thread burns CPU exactly under burst. Use
  `sink.emitNext(e, Sinks.EmitFailureHandler.busyLooping(duration))` (or a serialized
  sink); give up on FAIL_OVERFLOW/TERMINATED into the plan's overflow duty, never spin.
- INTEGRATION SLICE IS A PLANNED TEST, not a boot trick: the scaffold smoke
  (`contextLoads`) proves the graph RESOLVES; one @SpringBootTest slice with
  `WebTestClient` must drive the entry endpoint against the embedded substitute and
  assert DURABLE rows (valid payload persisted, invalid payload tagged, NOT rejected
  with a 5xx over an already-committed write). Scheduled by the architect, written by
  the tester, verified by the assembly gate's request-path probe.
- PERSISTENCE ADAPTERS PROVE SCHEMA FIT: every R2DBC/JDBC adapter slice test executes
  the REAL migration DDL against the embedded substitute (classpath resource or
  `ConnectionFactories` harness - the store-slice pattern) and asserts the inserted
  row back. A mocked `DatabaseClient` verifies call SHAPE only: NOT NULL floors, CHECK
  bounds and unpopulated PKs stay invisible until production traffic (2026-11-16:
  every audit write died on a NOT NULL `audit_id` no test had ever touched). Mocks are
  permitted as EXTRA shape cases beside the real-substrate one, never instead of it.
- LOG CORRELATION IS A DEPENDENCY, not a metaphor: when the strategy promises the
  correlation id in log lines, the plan must name micrometer
  `context-propagation` + `Hooks.enableAutomaticContextPropagation()` as a duty (the
  correlation unit or the wiring unit); without them Reactor Context never reaches
  the MDC and the ECS file loses the id at the first scheduler hop.
